## Confirmed defects and repairs

The old fixed-literal probe waited ten seconds, requested termination, then
waited five seconds. A second timeout escaped before its only result writer.
The missing receipt therefore did not establish either successful cleanup or
a particular PowerShell failure. The original failed attempt remains intact.

The historical 89-case driver used `subprocess.run(capture_output=True,
timeout=45)`. The inspected bundled Python 3.12 implementation's Windows timeout
path performs a further `communicate()` without a timeout after requesting
termination. That can wait indefinitely for pipe readers. The source proves an
unbounded harness path; it does not reconstruct the earlier process's stack.

The new `scripts/verify-host-readiness.py` uses direct file output, incremental
checked receipts, handle-derived PID/start/executable identity, and separate
primary and cleanup outcomes. Its default is inventory. An actual fixed-literal
probe requires explicit selection and the expected executable hash. It never
accepts an old PID or changes execution policy. Wait budgets do not promise to
bound an operating-system launch/termination call that itself never returns;
receipts precede those boundaries. Direct-child exit does not prove descendant
exit or final closure of inherited log writers.

The shared `ProcessJob` and `mod.Job.run` now retain cleanup failures without
replacing the original assignment/resume error, timeout, or cancellation.
Raw process records add PID, elapsed time, confirmed-exit status, and secondary
cleanup errors. A successful program return followed by failed cleanup is not
successful verification. Compiler source, runtime semantics, installed compiler,
active tool pointer and live MESH are unchanged by these repairs.

(`0xA0`) and subtype `0xF0`. Microsoft describes this subtype as a suspend

power-management failure for that restart, about twenty hours after the old
probe logs. It does **not** identify the stalled PowerShell thread, the responsible
driver, or a causal connection to the earlier shell failure.
[Microsoft bug-check reference](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0xa0--internal-power-error).
An unexpected-restart event alone cannot identify its cause.
[Microsoft Event 41 guidance](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/event-id-41-restart).

The precise historical PowerShell-stall cause remains unestablished. The host
is now demonstrably responsive. There is no evidence here establishing a Beryl
compiler defect, execution-policy denial, antivirus cause, or memory-exhaustion
cause. No operating-system or power setting has been changed.
