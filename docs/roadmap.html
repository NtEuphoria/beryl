Roadmap

The approved delivery program controls current implementation order: safety, verified execution, the complete tablet feature, shared AI tooling, deployment and measured performance. Follow the delivery state and exact verification gates. The SPARKOS plan and advanced performance program retain their detailed contracts; historical research is not implemented support.

The latest installed checkpoint adds bounded engine declaration lookup, array/Canvas probes, experimental record/PID IR parity and actual terrain collection. Its 34.06% median paired reduction covers command construction and release only; full-render, physical-resource and independent-session gates remain open. Public IR lowering and automatic optimization remain unavailable. See the exact checkpoint evidence and rollback record.

Current implementation: module and declaration identity and the bounded semantic reference have passed their documented gates. The complete SPARKOS PID port passed real engine parity, nine existing MESH suites, all 18 host gameplay checks and actual control handover in an isolated candidate on September 7. Dependable engine context and source mappings are in progress. The live MESH project remains unchanged; dedicated multiplayer and visual acceptance remain unverified. See the execution state for the installed compiler and exact test records.

v0.1 works: a 297 KB compiler, two back ends, and EnforceScript that compiles cleanly in real Workbench. This is the plan for everything it does not yet do — ordered by one argument about what Beryl is for, and gated on one experiment that could end the project.

Do this before building anything else

Port a real SPARKOS MESH class and ship it

Not an example — a class that is currently in the mod. Take SPK_MeshStore.c and SPK_PID.c out, rewrite them in Beryl, generate, delete the originals, run it in-game.

Then answer honestly:

  1. Was the loop actually faster, or did generating and re-generating eat the gain?
  2. Did anything break that the type checker should have caught?
  3. Was reading the generated script in Workbench tolerable when something did break?
  4. Would you do it again for the next class?

If the answer to (4) is no, stop and reconsider the whole project before writing another 10,000 lines. Everything else on this page is a plan for a thing that might not need to exist. This is the only part that tells you whether it does.

Why the ordering below is what it is

Beryl is two languages sharing one compiler

Beryl / Enfusion

(a) · ships first · the wedge

A better language for Arma Reforger mod logic. Write it once, test it natively in milliseconds, emit EnforceScript that Workbench compiles.

Beryl

(b) · a stated goal · years out

A general-purpose systems language competing with Rust — without the engine parts, built from the same compiler rather than a fork.

Both are goals. (a) ships first, because it is the wedge. (b) is the harder of the two by a wide margin: it needs generics, traits, concurrency, an ecosystem, a registry, an LSP, cross-platform support, years of hardening — and a pitch better than “like Rust, but younger with fewer libraries,” which is a losing one.

(a) has a moat, and it is a good one: nobody else can give you a fast test loop for EnforceScript. That advantage is structural — it comes from having a second back end — and no linter or editor plugin can copy it.

Taking that seriously reshuffles the obvious priorities considerably:

Note what that reshuffling is not: a demotion of (b). Everything on that list except the two Enfusion rows serves both editions — a real module system, working generics, a standard library, trustworthy codegen. The wedge is not a detour, it is the shared foundation with a customer attached.

How two languages ship from one codebase

Editions, not a fork

A fork buys separate branding and costs everything else: two bug fixes for every bug, two test suites, two sets of diagnostics drifting apart. For a 12,000-line compiler maintained by one person, that is the situation a fork ruins. And it buys nothing that packaging does not already provide.

The stronger argument is that the split already exists. Every line of Enfusion-specific code in v0.1:

WhereHow much
src/back/enforce_*.{c,h}1,331 lines
src/driver/main.c~11 lines — a CLI flag and its dispatch
src/driver/manifest.{c,h}~6 lines — the [target.enfusion] section
src/sema/zero. Every mention is a comment.
src/lex/, src/parse/zero. No mention at all.
The general edition is the current compiler minus 1,331 lines — roughly 11% of it. It already exists: beryl build with no -t enfusion is it.

The danger was never code coupling. It is design contamination — choosing a language semantic because Enfusion cannot do otherwise. One rule prevents it:

The rule that keeps the split free

Enfusion usefulness first, shared foundations for both targets

If a feature cannot lower to EnforceScript, profile-gate it — never remove it from the language. That is what BE0701, BE0703, BE0901 and BE0902 already do, pointed in both directions: a target profile gates what the target cannot express, and the language keeps it.

Auditing v0.1 against that rule, almost nothing has leaked. Monomorphization was forced by Enfusion but is correct anyway; !T losing its tag and value semantics via BerylCopy are lowering compromises, not language rules; the core kept every integer width the engine lacks. The profile-lint mechanism absorbed each constraint instead of the core absorbing it.

What “better than Rust” has to mean

Without a named axis it is not something you can build toward or ever know you have achieved. The axis that fits this design is systems programming for games and simulations.

Candidate advantages to verify

implementation and equivalent-workload evidence required

Graphs. Generational handles may fit game workloads. Beryl's Pool/Handle support remains proposed; Rust can also use handles.

Iteration speed. Measure real authoring tasks and rebuilds. Historical synthetic timing is not a Rust comparison.

No lifetime syntax, with complete storage safety still under development. Deterministic profiles remain proposals. Checked native arithmetic by default; Rust can configure release overflow checks too. No project build scripts or procedural macros.

Where Rust keeps winning

not gaps a design decision closes

crates.io — ~180,000 packages, which is a decade of other people's work.

Concurrency. Send/Sync is genuinely excellent, and Beryl has cut concurrency entirely.

Tooling — cargo, rust-analyzer, clippy, miri. Ten years of soundness work. Platform breadth: Beryl compiles on one OS today.

“Better than Rust” is achievable on an axis, not globally — where graphs are everywhere and Rust is most painful, where iteration speed dominates and Rust is slowest, where determinism matters and Rust offers nothing, and where the ecosystem gap is smallest because engines bring their own world. That is the same domain as the Enfusion edition: the two editions share a wedge, not just a compiler.

Everything known to be wrong or missing

The ledger

Correctness — these can burn you silently

#DebtWhy it matters
C1Codegen has 9 end-to-end programs guarding two back ends.A bug producing valid but wrong C passes clang, passes the type checker, passes every test, and ships. Costs you trust in the whole project.
C2pub is not enforced; use is decorative. Found while writing this document.A private function in another module is callable with no import. Any encapsulation you think you have, you do not have — and it gets worse the more code exists.

Capability — these block real use

P1No engine API bindings. Beryl knows nothing about IEntity, ScriptComponent, RplComponent. Only the pure-logic half of a mod can be written.
P2No component or RPC scaffolding. The paired …ComponentClass, editor attributes and RplRpc decorations are all hand-written.
P3lib/ is empty. There is no standard library written in Beryl at all — the directories were scaffolded and never filled.
P4No user-defined generics (BE0508).
P5No traits — they parse and are then ignored entirely.
P6Box, Rc, Pool, Handle do not exist (BE0902). The ownership model is designed around handles as the answer to “how do I build a graph”, and that answer is not implemented.
P7Map has no native representation and no methods on either target.
P8–P11No match or payload enums · no string formatting · no slices · no I/O beyond print.
P12Windows only. The compiler core is portable C11; three driver files are not.

Ergonomics and strategy

E1–E5No LSP · no beryl explain BE0401 · no package management · no generated API docs (despite //! comments already being parsed) · no incremental compilation.
S1The compiler is written in C — the largest single item on its own threat model.
S2Builds are not reproducible and cannot be while the Smart App Control workaround varies the binary per attempt. Two stated goals in direct conflict.
S3Two spec targets measured as failures: hello-world binary (< 20 KB claimed, 91.6 KB measured — unreachable on this toolchain) and overflow overhead (< 3% claimed, +82% measured).
S4@constant_time is a source-level lint that clang can undo. No optimization barriers are emitted.

The three ideas that carry the most weight

Keystones

The interpreter

A tree-walking interpreter over the typed AST, ~900 lines. The best-value item on the roadmap because it solves four problems at once.

1 · a differential oracle for codegen — the scariest gap, closed

2 · a near-instant test loop — and for the wedge, the test loop is the product

3 · unifies constant evaluation — comptime and const generics stop being special cases

4 · a REPL, nearly free

@rpc implies @untrusted

An RPC handler's parameters arrive from a client you do not control. That is true by definition — so it should not depend on a human remembering to annotate it.

@rpc(server)
pub fn Store.on_update(inout self,
        let slot: i32, let v: i32) {
    self.slots[slot] = v  // BE0601, automatically
}

This turns the most common real vulnerability in networked mods — trusting an RPC argument — into a compile error you cannot forget to switch on.

Trusting the code generator

More end-to-end programs is linear effort for linear coverage. Four better approaches:

Differential against the interpreter — every test program now tests codegen, and a random generator makes that arbitrarily many.

Metamorphic — rename bindings, reorder independent statements, wrap a body in a function; output must not change. Explores near real programs rather than uniformly.

Optimization-level — -O0 versus -O2. Any difference is a codegen bug or emitted UB.

Cross-target — run it natively, run the emitted EnforceScript headless in Workbench, compare. The only thing that can prove the two back ends agree.

Why self-hosting waits

It is the only real answer to S1 — a memory-safety language whose compiler is written in a memory-unsafe one. It is also downstream of almost everything: writing the compiler in Beryl needs generics, traits, a real module system, hashmaps, string building and file I/O.

And the risk arithmetic does not favour it:

fuzz lexer + parser~200 linesmost of the risk
ASan/UBSan in CI~1 daymost of the rest
arena-only allocationdonethe use-after-free class
self-hosting~12,000 linesthe remainder

On no list yet, and filtered by the thesis

Worth adding

Determinism, and why it matters here

A networked game where two machines simulate the same thing must get the same answer. Floating point makes that hard, and nothing in Beryl currently helps. Fixed-point types are deterministic across machines, compilers and optimization levels by construction — for a drone mod doing position integration, that is the difference between clients agreeing and clients drifting.

@deterministic forbids anything that varies: f32 arithmetic, sqrt, any non-deterministic extern. It turns “is this replay-safe?” from a code-review question into a compile error — and it is the same taint machinery with a different policy, which is the pattern that made the security work affordable in the first place.

Rust does not have this. EnforceScript does not have this. It is directly useful to the mod that motivated the project.

Compile-time serialization

@serialize derives a wire format for both targets. For a mesh networking mod this is enormous — hand-written pack/unpack is where protocol bugs live, and the two sides drifting apart is the classic failure. It composes with the above: a @serialize @deterministic struct is a network message you can reason about.

Units as newtypes

type Meters = f32 with no implicit conversion to Seconds — which Beryl's existing strictness makes natural rather than bolted on. Catches the classic flight-code bug of mixing degrees with radians. Cheap, and unusually well matched to the language's personality.

Testing beyond assert

Snapshot assertions — expect(v, "12.5") that self-update, ideal for controller output where the right answer is “whatever it was before I refactored”. Property tests over generated inputs, cheap to run once the interpreter exists. bench as a language construct — for a project whose README makes performance claims, benchmarks should not be a shell script.

Smaller, disproportionate

beryl explain BE0401 (~150 lines, embed the docs) · beryl doc (the //! comments are already parsed and stored) · @deprecated · const generics · format-on-save once there is an LSP.

Build scripts and proc macrosEver. This is the supply-chain guarantee, and it is worth more than the convenience.
